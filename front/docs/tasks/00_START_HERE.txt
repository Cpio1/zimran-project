Требование организаторов: MVP открывается сразу без регистрации, логина, пароля, обязательного email и экрана авторизации. Backend незаметно создаёт анонимную демо-сессию. Это требование имеет приоритет над прежними заданиями.

Это задания и контракты для разработки. Код самих трёх сервисов предстоит реализовать. Общие схемы и примеры проверены отдельно от будущего приложения.

Каждый участник получает весь архив, затем передаёт Claude Code свой TXT. Полное ТЗ и contracts доступны ему как контекст. Так все видят один продукт, но меняют разные папки.

2. ТРИ ЧАСТИ И ИХ СВЯЗЬ

Frontend: Next.js, порт 3000, папка apps/frontend.
Backend: FastAPI, порт 8000, папка services/backend.
LLM: FastAPI, порт 8001, папка services/llm.

Браузер вызывает только Backend.
Backend вызывает LLM по внутреннему API.
Backend подключён к Supabase и владеет пользовательскими данными.
LLM вызывает внешний API модели и возвращает JSON.
Frontend не подключается к Supabase. После открытия ссылки он сам получает анонимную демо-сессию у Backend. Экранов регистрации и входа нет.

Отдельный LLM-сервис позволяет разрабатывать и запускать его независимо. При внешнем API модели тяжёлый инференс выполняется у провайдера; локальная GPU не нужна. Распределение разработки по компьютерам не требует запускать модель на каждом.

3. ГДЕ ЛЕЖИТ КОД

Рекомендуется один общий Git-репозиторий с независимыми папками:
apps/frontend — свой package.json, lockfile, Dockerfile, README.
services/backend — свои Python-зависимости, worker, migrations, Dockerfile, README.
services/llm — свои Python-зависимости, промпты, OCR, Dockerfile, README.
contracts — общие схемы; отвечает интегратор.
fixtures — примеры; отвечает интегратор.
docs — документация интеграции.

Общие contracts и fixtures из архива положите в корень репозитория.
Текстовые задания и исходное ТЗ можно положить в docs/tasks.

Участники работают в собственных клонах на разных компьютерах. Не редактируйте одну общую сетевую папку.

Ветки:
work/front — Frontend.
work/back — Backend.
work/llm — LLM.

Обычная последовательность у каждого:
git clone <URL_РЕПОЗИТОРИЯ>
git switch -c work/front
или соответствующая work/back / work/llm.

Общие файлы должны попасть в main до старта трёх веток. Секреты остаются в локальных .env. У каждого компонента свой lockfile, чтобы уменьшить конфликты.

4. ЧТО НУЖНО СОГЛАСОВАТЬ СРАЗУ

Версия API: 2.0.0.
Имена маршрутов, полей и enum заданы OpenAPI.
Успех: data + request_id.
Список: data[] + next_cursor + request_id.
Ошибка: error {code, message, retryable} + request_id.
Деньги: целые центы USD.
Unknown: null.
Идентификаторы: UUID.
Даты: YYYY-MM-DD.
Техническое время: ISO 8601 UTC.
Часовой пояс: IANA string.

Idempotency-Key повторяется при retry той же операции. Новый пользовательский запрос получает новый ключ. Backend хранит результат и отклоняет другой payload с прежним ключом.

expected_version защищает PATCH/изменения использования от затирания новой версии. Конфликт — 409; Frontend запрашивает актуальное состояние.

Состояние Job отдельно от состояния документа и стадии дела.
Job: queued, running, succeeded, failed, cancelled, stale.
Document: uploaded, processing, needs_review, ready, failed.
Case: draft, prepared, submitted, awaiting_response, approved, denied, resolved.

Публичный POST /api/v1/demo/sessions без тела возвращает {data: {id, session_token, expires_at}, request_id}. Браузер сохраняет токен и передаёт X-Demo-Session во всех запросах данных. /health и создание сессии открыты; LLM и scheduler сохраняют отдельные серверные секреты. TTL сессии по умолчанию 7 суток. Одна фиксированная публичная сессия для всех не используется.

Для nullable/required и полных тел запроса используй JSON-схемы, а не пересказ в этом тексте.

5. ПРОИЗВОЛЬНЫЕ ИЗМЕНЕНИЯ КОНТРАКТА

Контракт заморожен для первой совместной реализации. Участник не может самостоятельно переименовать remaining_units в balance или вернуть другую форму ответа.

Если обнаружена необходимая правка:
- Описать изменение интегратору.
- Обновить оба OpenAPI из одного набора общих DTO.
- Обновить fixtures и версию.
- Проверить совместимость.
- Передать общий commit всем трём участникам.

Основное правило: сначала схема и пример, затем реализация изменения во всех затронутых частях. Внутренние функции и таблицы можно выбирать независимо, если внешний контракт соблюдён.

6. КАК КАЖДЫЙ РАБОТАЕТ БЕЗ ОСТАЛЬНЫХ

Frontend:
NEXT_PUBLIC_API_MODE=mock.
MSW/адаптер отвечает по backend.openapi.json и fixtures.
В http-режиме используются те же компоненты, только другой транспорт.

Backend:
Тестовый FakeLlmClient возвращает ответы fixtures по llm.openapi.json.
Настоящий HttpLlmClient готов к переключению через LLM_BASE_URL.
Supabase Postgres/Storage, migrations и проверки изоляции демо-сессий проверяются отдельно. Supabase Auth не нужен.

LLM:
Получает JSON-контекст или multipart с файлом из собственных тестов.
Не требует работающего Backend или Frontend.
Выполняет настоящие вызовы модели при наличии ключа.

Все тестовые режимы явные. В итоговой интеграционной проверке mocks выключены.

8. ПЕРВАЯ СВЯЗКА В НАЧАЛЕ РАБОТЫ

Не откладывайте первую проверку связи до завершения всех экранов.

Первый общий milestone:
- У каждого сервиса работает /health с contract_version.
- Backend вызывает защищённый LLM /answer на общем sample.
- Frontend получает Backend /health и один список через общий API client.
- Проверены автоматическое создание демо-сессии, X-Demo-Session, служебный LLM bearer token и CORS.

Это маленькая проверка интерфейсов. Полные сценарии добавляются по мере готовности. Так финальное объединение не начинается с обнаружения несовместимых форматов.

9. ОКОНЧАТЕЛЬНОЕ ПОДКЛЮЧЕНИЕ

Если все сервисы запускаются на одном компьютере:
Frontend:
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
NEXT_PUBLIC_API_MODE=http

Backend:
LLM_BASE_URL=http://localhost:8001
FRONTEND_ORIGINS=http://localhost:3000

LLM и Backend:
Одинаковый LLM_SERVICE_TOKEN в локальных .env.

Supabase:
Один проект Postgres/Storage на команду, серверные настройки получает только Backend. Supabase Auth не настраивается. Frontend и LLM никаких ключей Supabase не получают. Backend создаёт demo_session_id и проверяет opaque session_token.

Если сервисы остаются на трёх компьютерах:
- В Frontend API_BASE_URL указывает на сетевой адрес машины Backend.
- В Backend LLM_BASE_URL указывает на сетевой адрес машины LLM.
- CORS содержит фактический адрес Frontend со схемой и портом.
- localhost означает текущий компьютер; он не указывает на машину другого участника.
- LLM API доступен Backend, а не напрямую браузеру.
- Для передачи пользовательских документов вне локального окружения используется HTTPS.

В Docker:
Backend обращается к имени сервиса llm:8001, не к localhost.
Браузеру нужен доступный ему Backend URL: внутреннее имя контейнера backend для браузера не подходит.
NEXT_PUBLIC переменные Frontend учитываются на этапе сборки.

Интегратор может добавить compose после появления Dockerfile трёх сервисов. Не меняй API ради способа запуска.

10. ПОСЛЕДОВАТЕЛЬНОСТЬ ОБЪЕДИНЕНИЯ

В main объедините contracts/fixtures, затем изменения из work/back, work/llm и work/front. Исправляйте конфликты только с пониманием владельца файла; корневые контракты не выбирайте случайной стороной merge.

Пример команд после получения готовых веток:
git switch main
git pull
git merge origin/work/back
git merge origin/work/llm
git merge origin/work/front

Порядок merge не заменяет интеграционную проверку. Для финального запуска нужны:
- Применённые migrations/RLS.
- Созданный приватный bucket.
- Настроенное автоматическое создание demo_sessions без Supabase Auth.
- Запущенные Backend API и worker.
- Запущенный LLM с ключом модели.
- Frontend в http-режиме.
- Отдельная конфигурация email/scheduler, если проверяется доставка.

11. ОБЩИЙ ПРИЁМОЧНЫЙ ПРОХОД

1. Проверяющий открывает ссылку и сразу видит Home. Демо-сессия создаётся автоматически, без имени, email и пароля.
2. Создаёт запись и загружает реальный PDF сертификата.
3. Backend сохраняет файл и job.
4. Worker отправляет байты в LLM.
5. LLM возвращает страницы, факты, BenefitCandidate и цитаты.
6. Backend проверяет ответ и сохраняет Benefit с usage_state=unknown.
7. Frontend показывает результат и источник.
8. Пользователь подтверждает used=1 при total=4; остаток 3.
9. Повтор запроса не уменьшает остаток ещё раз.
10. Вопрос в чате получает ответ со ссылкой на тот же документ.
11. Создаётся дело benefit_use, появляется отдельный постоянный чат.
12. Генерируется и редактируется обращение.
13. Пользователь сам отправляет его и отмечает действие.
14. Добавляется ответ компании, затем follow-up.
15. Подтверждённый итог не удваивает использование и суммы.
16. Напоминание срабатывает один раз; изменение даты отменяет старое.
17. Другой браузер получает отдельную демо-сессию и не видит исходные документы или сообщения.
18. Удаление документа отменяет связанные процессы и источники.
19. Повторное открытие в том же браузере до истечения сессии сохраняет данные без входа.

Отдельно прогоните matching по сервисному договору, вопрос по страховке, отказ по гарантии и задержанный возврат из полного ТЗ.

12. ВАЛИДАЦИЯ ОБЩИХ ФАЙЛОВ

Из корня архива или репозитория:
python3 -m pip install -r contracts/requirements.txt
python3 contracts/validate_contracts.py

Проверяются структура общих JSON Schema, локальные ссылки, идентичность DTO в двух спецификациях и fixtures. Это проверка контрактов; она не доказывает работу ещё не реализованных сервисов.

13. РОЛЬ ЧЕТВЁРТОГО УЧАСТНИКА

Если команда остаётся из четырёх человек, четвёртый может быть интегратором: следить за общим контрактом, запуском Supabase и окружения, интеграционными проверками и демо. Три основные части распределяются по одному владельцу.

Не обещайте отсутствие любой доработки при объединении. Цель контракта — сделать границы известными заранее, чтобы финальные исправления касались интеграции, а не переписывания трёх приложений.
