ТЗ ДЛЯ CLAUDE CODE — BACKEND

Требование организаторов: MVP открывается сразу без регистрации, логина, пароля, обязательного email и экрана авторизации. Backend незаметно создаёт анонимную демо-сессию. Это требование имеет приоритет над прежними заданиями.
Рабочая папка: services/backend
Ветка: work/back
Сервис: Python + FastAPI, порт 8000.
Ты отвечаешь только за Backend. Реализуй работающий сервис и проверки, не ограничивайся планом.

Общий контекст для всех трёх частей
Claimly — B2C веб-приложение для пользователей США 25–45 лет. Оно хранит гарантии, страховки, сервисные договоры, сертификаты, условия членств, чеки и возвраты; находит оплаченные или бесплатные преимущества; напоминает об использовании; отвечает по документам; помогает с обращениями и результатами.
Четыре модуля MVP: Vault; Benefits и Reminders; Assistant и Benefit-to-Need Matching; Claims и Case Tracking.
Полный объём: 99_Product_MVP_Source.txt. Архитектура и обязательные правила: 00_START_HERE.txt. Машинные контракты: contracts/backend.openapi.json и contracts/llm.openapi.json, версия 2.0.0. Примеры: fixtures/*.json.

Правила совместимости
- Сначала прочитай общий контекст, контракты и примеры. Не переименовывай поля, статусы, маршруты или enum под свой вкус.
- Изменение contracts/* согласуется с интегратором и применяется у всех. Обычные внутренние реализации выбирай самостоятельно.
- Успех HTTP: {data, request_id}; список: {data: [], next_cursor, request_id}; ошибка: {error: {code, message, retryable}, request_id}. 204 не содержит тела.
- Неизвестные значения — null. ID — UUID. Даты — YYYY-MM-DD, техническое время — ISO 8601 UTC. Деньги — целые центы; валюта USD.
- Следуй назначению required и nullable в OpenAPI. Списки со страничной выдачей сортируются стабильно.
- У дорогих и повторяемых операций используй Idempotency-Key; повтор с тем же ключом возвращает тот же результат, другой payload с этим ключом — 409.
- Во всех ответах добавляй X-Contract-Version: 2.0.0. /health возвращает статус сервиса и contract_version.
- Нельзя выдавать sample-ответ за настоящий анализ. У функций без ключей — честное состояние и инструкция настройки.


1. ГРАНИЦА ОТВЕТСТВЕННОСТИ

Ты владеешь:
- HTTP API для Frontend.
- Автоматическими демо-сессиями, изоляцией данных, БД и Storage.
- Состояниями документов и задач.
- Вызовами внутреннего LLM API.
- Сохранением результатов, источников, чатов и истории.
- Поиском разрешённого контекста для ИИ.
- Детерминированными сроками, использованием преимуществ и результатами.
- Календарём, напоминаниями и email-доставкой.
- SQL-миграциями и серверной конфигурацией.

Frontend не обращается к таблицам и Storage напрямую. LLM не получает ключи Supabase и не пишет в БД. Решения о доступе и изменении состояния принимает Backend.

2. СТЕК И СТРУКТУРА

FastAPI, Pydantic, HTTP-клиент для LLM и Supabase Postgres/Storage. Python-зависимости и lockfile храни внутри services/backend. Сервис запускается независимо от двух остальных.

Supabase используется только для БД и приватного Storage. Не подключай Supabase Auth, регистрацию, пароли, OAuth или JWT пользователей. POST /api/v1/demo/sessions без тела и без предварительного токена автоматически создаёт отдельное демо-пространство и возвращает DemoSessionEnvelope. Создай session_token из минимум 32 случайных байтов, храни только его hash; срок по умолчанию 7 суток. Все последующие запросы данных содержат X-Demo-Session. По токену Backend определяет session_id, а не принимает владельца из тела запроса. Ограничь частоту создания сессий. Сырые токены не логируй.

Храни SQL migrations и RLS policies внутри services/backend/migrations. Во всех пользовательских таблицах владелец — demo_session_id. Прямой доступ из браузера к БД/Storage запрещён. RLS не заменяет серверную фильтрацию по demo_session_id, особенно при service_role. Проверяй также связи между объектами.

3. РЕАЛИЗУЙ API КОНТРАКТА

Точный список 43 операций — в contracts/backend.openapi.json. Не придумывай параллельные маршруты.

Основные группы: profile, dashboard, entries, documents, benefits, threads/messages, cases/events/replies/drafts/outcome, reminders, notifications, jobs.

Особенности:
- POST /api/v1/documents принимает multipart entry_id + file, сохраняет оригинал, создаёт задачу и возвращает 202 UploadAcceptedEnvelope.
- Файл принадлежит существующей записи пользователя. Для новой загрузки Frontend сначала создаёт запись.
- GET /api/v1/documents/{id}/content выдаёт байты после проверки доступа; секретный публичный URL не нужен.
- Сообщение чата сохраняется до вызова ИИ. POST messages возвращает user message + Job; результат приходит через GET jobs.
- Оценка, создание черновика и разбор ответа компании также возвращают Job.
- Черновик редактируется отдельно, без автоматической отправки.
- Idempotency-Key обязателен там, где указан в контракте.

4. ФАЙЛЫ И ЗАДАЧИ

Допустимы PDF/JPEG/PNG, 10 MB на файл, 25 страниц на документ; до пяти файлов за пользовательскую загрузку обрабатываются отдельными запросами.

Backend проверяет тип, размер, сигнатуру, владельца и сохраняет файлы приватно. LLM-компонент отвечает за PDF parsing, OCR и извлечение страниц.

Создай сохраняемую очередь Job в Postgres и отдельный worker-процесс. HTTP создаёт job, worker исполняет, Frontend опрашивает состояние. Не делай fire-and-forget после ответа HTTP.

Worker:
1. Атомарно захватывает job с lease/защитой от одновременного выполнения.
2. Считывает актуальные файлы и версии.
3. Отправляет данные LLM-сервису по соответствующему контракту.
4. Проверяет ответ и принадлежность всех ссылок.
5. В одной транзакции сохраняет результат и состояние job.
6. Проверяет, что документы и версии не изменились за время обработки.

Для extract передавай multipart file + metadata, соответствующий ExtractRequest, в /internal/v1/extract. Не пересылай внешние URL для скачивания.

Перезапуск worker не должен терять jobs. Ограничь повторы и время вызова. Не дублируй преимущества при повторе успешной задачи. Удалённые или изменённые данные делают старую задачу cancelled или stale; её результат нельзя применять.

5. КОНТЕКСТ ДЛЯ ИИ

LLM_BASE_URL и LLM_SERVICE_TOKEN используются только сервером. Реализуй адаптеры ко всем шести операциям LLM-контракта.

Backend собирает LlmContext:
- Только записи и документы текущей демо-сессии.
- Для case — только явно связанные документы и история этого дела.
- Для entry — документы этой записи.
- Для vault — релевантные результаты поиска по разрешённым записям и преимуществам.
- Актуальные подтверждённые факты, остатки и даты.
- Реальное as_of и timezone.

Сначала можно использовать PostgreSQL full-text/поиск по полям. Векторная БД не обязательна. LLM не выбирает объекты из чужой БД самостоятельно.

Любой matched_benefit_id, EvidenceRef и target_id в ответе проверяй против разрешённого контекста. Источники включают document_version. Цитата должна существовать на указанной странице.

6. СРОКИ И ИСПОЛЬЗОВАНИЕ

LLM возвращает DeadlineRule, а окончательные даты считает Backend. Явная дата и однозначные календарные интервалы поддерживаются кодом; business days без календаря и неизвестная точка отсчёта требуют проверки. Не интерпретируй напечатанную дату как окончательный юридический вывод.

Преимущество после извлечения имеет usage_state=unknown, used_units=null, remaining_units=null, пока пользователь не подтвердит использование.

PUT /benefits/{id}/usage задаёт абсолютное число использованных единиц, а не приращение. Пример: total=4, used=1 → remaining=3. Повтор того же запроса оставляет 3. Создавай внутреннюю историю изменений. Проверяй версии, неотрицательность и верхнюю границу, если total известен.

Plan to use и создание дела не списывают услуги.

7. РЕЗУЛЬТАТ И ДВОЙНОЙ УЧЁТ

PUT /cases/{id}/outcome сохраняет актуальный итог одного дела. Для cash_refund cash_amount_cents обязателен; для неденежных результатов он null. Оценочная стоимость хранится отдельно и не попадает в cash_recovered.

Для service_used/voucher_used с benefit_id обновление итога и внутреннего usage-события выполняется атомарно и привязано к outcome_id. Изменение количества корректирует прежнее событие, а не добавляет второе. При неизвестной исходной истории уточни baseline, прежде чем вычислять полный остаток.

Dashboard services_used_units считает подтверждённое использование преимуществ один раз; связанные outcomes дополнительно не суммирует. Неденежный исход без benefit_id учитывается отдельно. Реализуй проверку общего сценария: baseline → использование → outcome → повтор outcome → исправление.

8. НАПОМИНАНИЯ

Сохраняй правила, timezone, время, выбранные интервалы 30/14/7/1/0, каналы и состояние. Каналы — in_app и email; для email нужны добровольно указанный notification_email, согласие и рабочая конфигурация. Email не является логином и не нужен для проверки MVP.

Защищённый /internal/v1/reminders/dispatch вызывается планировщиком по отдельному SCHEDULER_SECRET. Этот endpoint относится к Backend, не к LLM.

Уникальный ключ доставки: reminder + revision + interval + channel. Повторы scheduler не дублируют отправку. Храни pending/sent/failed/cancelled и ограниченные повторы.

Изменение даты, использование услуги, закрытие дела или удаление источника отменяет неактуальные уведомления. Технические даты UTC, пользовательская дата и время — в IANA timezone с учётом DST.

9. ДАННЫЕ И БЕЗОПАСНОСТЬ

Нужны demo_sessions, session_preferences, entries, documents/pages, benefits, usage_events, threads/messages, cases/events/drafts/outcomes, jobs, reminders/deliveries. Связи принадлежат одной demo_session_id; session_preferences используются DTO Profile и не являются учётной записью. JSONB допустим для фактов и источников; DTO API должны совпадать с контрактом.

Удаление оригинала отменяет jobs и напоминания, удаляет файл и делает зависимые выводы неактуальными. После удаления источника цитаты не должны продолжать открывать удалённые данные. Сохранение оставшихся источников и связей проверь отдельно.

Добавь CORS только для FRONTEND_ORIGINS с разрешением заголовка X-Demo-Session, ограничения частоты, корректные ошибки, защищённые логи и валидацию входа. Cookie-based login не нужен. Отсутствующая или истёкшая демо-сессия даёт 401 с DEMO_SESSION_REQUIRED/DEMO_SESSION_EXPIRED. Frontend может автоматически начать новую сессию, но Backend не должен переносить данные между сессиями. Текст документов и секреты не логируй.

10. АВТОНОМНАЯ РАЗРАБОТКА

Реализуй HttpLlmClient для настоящего сервиса и FakeLlmClient исключительно для тестов и явного DEV_LLM_STUB=true. Заглушка использует общие fixtures и не включается молча. Работа с реальным Supabase обязательна для серверной интеграционной проверки.

Frontend не нужен для локальных проверок: используй pytest/HTTP-клиент. Подготовь README с последовательностью API-запросов.

12. ПРИЁМКА И ПЕРЕДАЧА
