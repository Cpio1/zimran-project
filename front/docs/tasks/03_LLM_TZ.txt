ТЗ ДЛЯ CLAUDE CODE — LLM SERVICE

Требование организаторов: MVP открывается сразу без регистрации, логина, пароля, обязательного email и экрана авторизации. Backend незаметно создаёт анонимную демо-сессию. Это требование имеет приоритет над прежними заданиями.
Рабочая папка: services/llm
Ветка: work/llm
Сервис: Python + FastAPI, порт 8001.
Ты отвечаешь за обработку документов и ответы ИИ. Создай работающий внутренний сервис, не ограничивайся коллекцией промптов.

Общий контекст для всех трёх частей
Claimly — B2C веб-приложение для пользователей США 25–45 лет. Оно хранит гарантии, страховки, сервисные договоры, сертификаты, условия членств, чеки и возвраты; находит оплаченные или бесплатные преимущества; напоминает об использовании; отвечает по документам; помогает с обращениями и результатами.
Четыре модуля MVP: Vault; Benefits и Reminders; Assistant и Benefit-to-Need Matching; Claims и Case Tracking.
Полный объём: 99_Product_MVP_Source.txt. Архитектура и обязательные правила: 00_START_HERE.txt. Машинные контракты: contracts/backend.openapi.json и contracts/llm.openapi.json, версия 2.0.0. Примеры: fixtures/*.json.

Правила совместимости
- Сначала прочитай общий контекст, контракты и примеры. Не переименовывай поля, статусы, маршруты или enum под свой вкус.
- Изменение contracts/* согласуется с интегратором и применяется у всех. Обычные внутренние реализации выбирай самостоятельно.
- Успех HTTP: {data, request_id}; список: {data: [], next_cursor, request_id}; ошибка: {error: {code, message, retryable}, request_id}. 204 не содержит тела.
- Неизвестные значения — null. ID — UUID. Даты — YYYY-MM-DD, техническое время — ISO 8601 UTC. Деньги — целые центы; валюта USD.
- Следуй назначению required и nullable в OpenAPI. Списки со страничной выдачей сортируются стабильно.
- У дорогих и повторяемых операций используй Idempotency-Key; повтор с тем же ключом возвращает тот же результат, другой payload с этим ключом — 409.
- Во всех ответах добавляй X-Contract-Version: 2.0.0. /health возвращает статус сервиса и contract_version.
- Нельзя выдавать sample-ответ за настоящий анализ. У функций без ключей — честное состояние и инструкция настройки.


1. ГРАНИЦА ОТВЕТСТВЕННОСТИ

Ты владеешь PDF parsing/OCR, классификацией, извлечением фактов и преимуществ, промптами, структурированными ответами, вопросами по контексту, matching, оценкой ситуации, черновиками и разбором ответа компании.

Сервис не имеет своей пользовательской БД, Supabase credentials, очереди, системы email, календарного движка или браузерного интерфейса. Не изменяет статус дела и не списывает услуги.

Backend передаёт разрешённые данные, хранит результат и выполняет бизнес-действия. LLM-сервис возвращает структурированный результат.

2. API И КОНТРАКТ

Реализуй точные маршруты contracts/llm.openapi.json:
GET /health
POST /internal/v1/extract
POST /internal/v1/answer
POST /internal/v1/match
POST /internal/v1/assess
POST /internal/v1/draft
POST /internal/v1/analyze-reply

Все POST защищены Authorization: Bearer LLM_SERVICE_TOKEN. Это серверный секрет, отличный от токена модели и токена демо-сессии. Отсутствие экрана входа у пользователя не отменяет закрытый служебный API: LLM_SERVICE_TOKEN остаётся только у Backend и LLM. К браузеру сервис не подключается.

Вход содержит request_id и contract_version=2.0.0. Ответ: {data, request_id, contract_version}. Ошибка соответствует общему ErrorEnvelope с корректным HTTP-кодом. Дорогие операции здесь синхронны с timeout; внешней очередью владеет Backend.

3. EXTRACT

Вход multipart:
- metadata — JSON-строка по ExtractRequest.
- file — реальные байты PDF/JPEG/PNG.

metadata задаёт стабильные document_id и document_version. Используй их во всех EvidenceRef. Не придумывай новые UUID.

Проверь размер, MIME/signature и лимит 25 страниц, защищённые/повреждённые файлы. Не скачивай произвольный URL.

Текстовый PDF разбирай по страницам. Для сканов и фотографий — реальный OCR или vision. В результате ExtractionOutput верни страницы, категорию, title/provider/subject, facts, BenefitCandidate и review_flags.

Категории включают страховки, сервисные договоры, сертификаты и членства, а не только гарантии. Один документ может дать несколько преимуществ.

Для каждого преимущества:
- Что входит.
- Условия.
- Количество или явно указанный номинал.
- DeadlineRule.
- Инструкции.
- EvidenceRef.
- Необходимость проверки.

Не возвращай usage_state, used_units или remaining_units в кандидате: ты не знаешь историю использования. Backend создаёт Benefit со значением unknown.

4. ИСТОЧНИКИ И ДОСТОВЕРНОСТЬ

Цитата должна быть точным фрагментом текста указанной страницы после нормализации пробелов. Для изображения page=1. Если страницу прочитать невозможно, укажи проблему, не создавай текст наугад.

Unknown — null. Не придумывай даты, лимиты, контакты, email или бесплатные услуги. Разделяй факт наличия условия и его применимость к ситуации.

Для страховки извлекай названные покрытия, deductible, лимиты и исключения, если они есть. Лимит полиса не является обещанной выплатой.

Для сертификата напечатанная дата не означает универсальную юридическую утрату прав. Для гарантии не подменяй дату поломки сегодняшней датой. Не объявляй обычное истечение покрытия автоматически отказом в уже наступившем случае.

DeadlineRule описывает исходное правило. Окончательную дату и доставку считает Backend. Не считай business days по выдуманному календарю.

5. ANSWER И MATCH

Используй только LlmContext, предоставленный Backend. Данные хранилища самому не запрашивай. as_of и timezone приходят от Backend; системные часы и память модели не заменяют подтверждённые даты.

Верни LlmAnswer:
- answer.
- evidence_refs.
- matched_benefit_ids из переданного контекста.
- questions.
- next_actions из допустимого enum.

У answer учитывай историю текущего диалога и case. У match сопоставляй реальную потребность с условиями услуги, нужным объектом, периодом и известным использованием.

Пример: автомобильная диагностика не всегда равна обязательному техническому осмотру; при неоднозначности спроси уточнение. Никакого совпадения — честный ответ без выдуманного преимущества.

Если сертификат содержит 4 услуги, но использованное количество неизвестно, спроси об истории использования. Не утверждай, что осталось 4.

6. ASSESS

Верни Assessment со статусом possible, insufficient_evidence или likely_excluded. Нужны summary, reasons, evidence_refs, missing_info, next_actions.

possible означает основания для запроса по документам, а не одобрение. Отсутствие важного документа — insufficient_evidence. likely_excluded требует соответствующего пункта и сопоставления с фактами.

Не применяй законодательство из общих знаний. Страховые, гарантийные и возвратные условия проверяй только в границах предоставленного контекста.

7. DRAFT И ANALYZE-REPLY

DraftRequest.kind задаёт initial либо follow_up. Возвращай DraftContent без самовольного изменения case status.

Поля: subject, body, attachments, contact, contact_origin, evidence_refs, missing_info. Используй подтверждённые факты, нейтральный тон и понятную просьбу. Не придумывай юридические угрозы, дату обращения, адрес получателя и номер заказа.

analyze-reply:
- Перескажи ответ.
- Выдели позицию компании.
- Сравни её с условиями.
- Покажи расхождение или отсутствие оснований для вывода.
- Предложи действие и необходимые сведения.

Ответ компании в reply_text считается пользовательски предоставленным текстом; он не даёт права придумывать документальную цитату. EvidenceRef на ответ допустим только при наличии соответствующих страниц в context.documents. В остальных случаях сошлись на текст ответа в объяснении, а document refs оставь для существующих документов.

8. СХЕМЫ, ПРОВЕРКИ И ЗАЩИТА

Вход и выход валидируй Pydantic-моделями, совпадающими с общим контрактом. Проверяй, что refs, benefit IDs и action target IDs есть в контексте.

Структурированный ответ модели проверяется до отправки Backend. Допустима одна попытка исправить неправильный JSON; затем INVALID_LLM_OUTPUT. Не маскируй невалидный результат успехом.

Документ и сообщения — недоверенные данные. Отдели системные инструкции и контекст, защити от команд внутри документа. Не используй произвольный HTML как выполняемый код.

Не логируй полный документ, секреты и личные идентификаторы. Временные файлы очищай. Таймаут и размер контекста ограничь; страницы нельзя терять незаметно.

9. ПРОВАЙДЕР И ОБОРУДОВАНИЕ

Основной путь — внешний API модели через серверный адаптер. Локальная GPU не требуется. Опциональную локальную модель не делай обязательной зависимостью.

.env.example:
LLM_SERVICE_TOKEN
MODEL_PROVIDER_API_KEY
MODEL_NAME
MODEL_BASE_URL
MODEL_TIMEOUT_SECONDS
MAX_FILE_MB=10
MAX_DOCUMENT_PAGES=25

Не выбирай слишком тяжёлую инфраструктуру для MVP. Для текста можно использовать обычную модель со строгим JSON; для OCR/vision — доступный реальный провайдер. Все обращения измеряй по latency и числу неуспешных ответов без раскрытия содержимого.

Без ключа верни AI_NOT_CONFIGURED. Фикстуры — только для явного тестового режима, а не скрытый fallback.

10. АВТОНОМНАЯ РАЗРАБОТКА И ПРИЁМКА

Backend и Frontend не нужны: тестируй свои endpoints на fixtures и небольших вымышленных документах.

Создай реальные sample PDF/image для:
- Сервиса кофемашины с одной бесплатной профилактикой.
- Сертификата на четыре стоматологические услуги.
- Гарантии ноутбука и исключения повреждений.
- Страхового пункта с условиями.
- Сервисного плана с диагностикой.
- Возврата с известным и неизвестным сроком.
- Нечитаемого документа и prompt injection в документе.

Проверь точность полей и цитат, unknown, отсутствие придуманных услуг, контекст дела, match без результата, initial/follow-up, malformed JSON, timeout и посторонний ID в ответе.

Предоставь README с запуском на 8001, примерами multipart/JSON-запросов, тестами и оценкой ограничений; .env.example; Dockerfile. Зависимости/lockfile только services/llm.
Не редактируй apps/frontend, services/backend и общие contracts без согласования.
